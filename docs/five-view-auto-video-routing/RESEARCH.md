# 五视图与自动视频路由研究

## 目标

把现有“三视图”人物一致性模板升级为严格五视图，并让九宫格分镜到运镜视频之间共享同一份不可漂移的镜头契约。视频生成模式由系统根据镜头意图、输入素材和运行时模型能力自动判断，同时保留人工显式选择。

## 用户故事

- 角色设计师生成同一人物、同一服装、同一发型和同一体型的五等宽横向视图：正面、正面四分之三、标准侧面、背面四分之三、背面。
- 分镜师产出严格 3×3 九宫格，每格包含角色、场景、道具、特效、景别、机位、运镜、首末状态和连续性信息。
- 视频生成器在首尾帧、多图/宫格、多模态参考之间自动选择合适模式，并说明选择或降级原因。
- 运镜提示词只能从对应分镜契约派生，不能改变人物、场景、道具、特效、构图轴线或首末状态。

## 当前实现审计

- 已有严格五视图提示词和 `FIVE_VIEW_ORDER` 数据约束。
- 已有恰好九格的 `NineGridStoryboard`，以及逐格分镜图片生成。
- 已有首帧、首尾帧、多图和多模态引用的数据传输能力。
- 现有 `auto` 只按“是否有素材”排序：角色参考图一出现就会优先多图，无法理解镜头是否必须精确到达尾帧，也没有供应商能力协商。
- 分镜和视频虽使用相近字段，但缺少可校验的共享指纹，后续提示词可能发生语义漂移。

## 官方能力核对原则

供应商能力按运行时能力档案协商，不把产品宣传或用户列出的候选模型直接当成已接通 API：

- MiniMax H3：项目已有适配器，支持首尾帧和参考素材请求。
- Seedance：项目已有通用生成适配路径；具体 2.0/2.5 模型是否可用、支持哪些模式，以配置端点和运行时能力为准。
- Kling：官方资料确认首尾帧、1–4 个 Elements 参考，以及 O1 的图像/视频多模态输入；只有配置了运行时端点才参与真实提交。
- Grok Imagine：官方 API 支持首帧图生视频和多参考图模式；当前参考模式不等同于音频参考。
- LTX-2.3：官方资料明确文生视频、图生视频和音频生视频；未核实的“九宫格多图同请求”不作为硬编码事实。
- HappyHorse：公开资料显示图像、视频、音频和文本多输入以及最多 9 张图，但公开站点/聚合接口差异较大，因此必须通过运行时配置确认后才可付费提交。

## 方案比较

### 方案 A：让语言模型自由输出模式和供应商

优点是表面灵活；缺点是不可重复、可能选择未配置或不兼容的供应商，也难以在付费调用前失败关闭。

### 方案 B：只看素材数量的固定优先级

实现简单，但不能理解“必须命中尾帧”“九格是叙事序列”或“视频/音频用于节奏”的意图。

### 方案 C：类型化决策引擎 + 能力协商（采用）

先从分镜契约提取控制目标并打分，再与候选模型能力求交集。选择结果包含模式、供应商、分数、理由、降级链和契约指纹。决策可测试、可追溯，也允许未来接入语言模型分类器，但最终仍由硬约束校验。

## 数据契约

每个镜头固定以下字段：

- `shot_id` 与九宫格位置；
- 角色、场景、道具、特效；
- 景别、机位、焦段、构图、动作轴线、运镜；
- 主体动作、表情、对白、声音、灯光；
- `start_state`、`end_state`、`continuity_in`、`continuity_out`；
- 分镜图片和所有引用素材；
- 规范化 JSON 的 SHA-256 契约指纹；
- 自动选择的模式、供应商、理由和降级信息。

视频提示词由这份契约编译，编译结果携带同一指纹。若分镜改动，旧视频计划自动视为过期。

## 风险与控制

- 供应商 API 快速变化：能力档案必须可配置并在付费前协商；未经验证的档案不自动提交。
- 多种模式可能同时满足：精确尾帧优先于一般多图，真正的视频/音频节奏参考优先多模态，九宫格叙事序列优先多图。
- 角色参考图不应永远抢占首尾帧：角色五视图作为一致性约束保留在契约中，但模式必须以镜头控制目标为主。
- 用户粘贴过真实密钥：密钥不写入文档、源码、日志或测试，也不执行付费调用。

## 验收标准

- 指定 Markdown 不再以三视图描述角色，并包含严格五视图顺序和禁用项。
- 五视图与九宫格约束有自动测试。
- 自动路由覆盖首尾帧、多图/宫格、多模态、首帧降级和无兼容供应商五类路径。
- 分镜与视频计划指纹一致；篡改任一关键字段会使校验失败。
- 全部离线测试、静态检查和构建通过。
